# Datamodel draft of core objects

**1. Projects Table:**
    * `project_id`: uuid (PK)
    * `name` string
    * `description` string (maybe not needed?)
    * `project_type` audio or video
    * `created_at` datetime
    * `updated_at` datetime
  
Stores the central header for each client project.

**2. Media Table:**
    * `media_id`: uuid (PK)
    * `filename` string
    * `storage_type` local or external service
    * `path` string (url or path to file)        
    * `mime_type` string (could possibly replace with some kind of more descriptive codec information)
    * `created_at` datetime    
    * `hash` string (could replace uuid?)
 
Actual file information and storage details (local or external service). The intent is to centralize the logic for accessing files, to have a kind of a single source of truth. The `mime_type` will be crucial for the backend to serve the correct content and also for the frontend to handle it appropriately.

**3. Project Primary Media Table:**
    * `project_id`
    * `media_id` or hash
    * `type`: primary deliverable, supplementary media, hidden, source file, etc...

A linking table which makes it possible create a relationship between `Projects` and `Media` files, with an additional categorization. This allows us to mark files as a primary deliverable, behind-the-scenes media, source file, and the likes of that. A many-to-many relationship is possible too, eg. a BTS photo can be both supplementary media and a thumbnail for the project. Some checks will need to be made by the backend to prevent nonsense states.
