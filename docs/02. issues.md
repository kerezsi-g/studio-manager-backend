# Handling iterative feedback from clients

**Issues Table:**
* `issue_id`: uuid (PK)
* `project_id`: uuid
* `description`: string
* `t_start`: start time of the problematic part in the relevant media, nullable
* `t_end`: end time of the nullable
* `resolved_at`: timestamp of when the issue was resolved, null if not resolved
* `created_at`: timestamp of when the issue was created

**Some points to make**:

* Both the `t_start` and `t_end` fields are nullable, which means they can be used to specify a specific point in time or a range of time within a media file, or a more general problem applicable to the whole of the relevant media if both are null
* The `resolved_at` field is nullable makes it so we don't require a separate boolean flag to mark the issue as resolved. It can be considered unresolved if the field is null
* The initial idea was to explicitly link issues to media files, but this was let go of. Using the `created_at` and `resolved_at` fields, we can track which deliverable resolved the issue without explicit links to a file.

**Why there is no implementation of back and forth commentary**:

There was an idea to have such functionality, but after some contemplation, I decided to instead keep it simple and straightforward. The purpose of this software is not to replace human communication with something more cumbersome, but to support it. The key information here are the timestamps. Clarifications and comments can be provided in other channels, such as text messaging, or what's much more likely: phone calls. Forcing yet another messaging app on users is most certainly not a good idea in my opinion.
